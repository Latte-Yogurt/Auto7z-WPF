# 测试生命周期硬性规范

> **本文是硬性指标，不是建议。**
> 任何对 `testtools/` 的改动都必须符合本文；违反者视为回归。
> 依据：2026-11-22 LTS 轮确立。此前多轮出现过「并行跑出 23 项假失败」
> 「一个套件清空了另一个套件正在用的目录」「残留 GUI 进程锁住数据目录导致下一轮清理失败」
> 等事故，根因全部是没有统一的生命周期约束。

---

## 一、三个阶段（主框架）

整轮测试就是三件事，顺序不能变：

```
阶段一 清理环境 + 准备测试
   ↓
阶段二 按串行顺序测试   ← 中途不清理环境
   ↓
阶段三 清理环境 + 结束测试
```

| 阶段 | 做什么 | 关键约束 |
|---|---|---|
| **一、清理并准备** | 清上一轮遗留、建目录、检查依赖、置环境变量 | 这是整轮**仅有的两次**允许全局清理之一 |
| **二、串行测试** | 逐个用例执行 | **中途不做全局环境清理**；每个用例靠自己的配置键/资源做到互不干扰；串行执行 |
| **三、清理并结束** | 清整轮产物、收残留进程、恢复环境 | 整轮**仅有的两次**允许全局清理之二；失败也要执行 |

### 核心原则（必须背下来）

> **全局环境清理只发生在整轮测试的开始与结束（阶段一与阶段三）；
> 阶段二内部只允许管理测试自身拥有的资源，
> 不允许清理环境、不允许破坏其他测试可能依赖的共享状态。**

这是整份规范里最重要的一条。违反它的典型症状：
- 测试 A 跑完后清空了 `%TEMP%`，测试 B 的配置没了 → B 假失败
- 某个 `finally` 里删了整个数据根 → 后续所有用例读到默认配置
- 中途清了环境变量，产品写回真实用户目录 → 污染用户配置
- 两个套件并行时互相覆盖配置 → 偶发、不可复现的失败

### 阶段二为什么必须串行

并行会带来一系列独占与竞态问题：

| 问题 | 影响 |
|---|---|
| 配置键冲突 | A 改配置 → B 读到错配置 |
| 数据竞争 | 一个测试删掉另一个正在用的数据 |
| 资源独占 | 争抢同一端口 / 设备 / 文件 / 互斥体 |
| 环境清理冲突 | 一个测试清环境，另一个还在跑 |
| 状态污染 | 前一个的状态影响后一个的结果 |

**本项目特有的硬约束**：产品有**单实例互斥体**。并行跑两套测试时，
第二套拿不到互斥体，表现为 `taborder` 报「走查中焦点丢失」这类假失败 ——
本轮就实际踩过一次（回归 + 系统测试同时跑 → 系统测试 1 项失败，串行重跑 18/18 全绿）。

### 阶段二如何做到「互不干扰」而不靠清理

不是靠"跑完就清"，而是靠**归属隔离**：

| 隔离维度 | 做法 |
|---|---|
| 数据目录 | 每套件独立根 `%TEMP%\Auto7zTest_data\<suite>`，产品数据只写这里 |
| 用例资源 | 每用例独立目录 `cases\<case>\`，通过 `own()` 登记 |
| 配置键 | 用例只碰自己声明的键；共享键只读不改 |
| 子进程 | `track_process` 登记，阶段三统一收尾 |
| 环境变量 | 只由阶段一设置、阶段三恢复，阶段二只读 |

## 二、五个实现阶段（三阶段的落地细节）

三阶段在实现上展开为五个钩子，一一对应：

| 钩子 | 归属主阶段 | 时机 | 允许动什么 | 禁止动什么 |
|---|---|---|---|---|
| **BeforeAll** | 阶段一 | 整轮开始前 | **允许全局清理**：清遗留、建目录、检查依赖、置环境变量 | —— |
| **BeforeEach** | 阶段二 | 每用例开始前 | **只初始化当前用例自己的资源** | 碰任何共享状态 |
| **Execute** | 阶段二 | 用例执行 | 用例自身 | **做任何全局环境清理** |
| **AfterEach** | 阶段二 | 每用例结束后 | **只清理当前用例登记过的资源** | 清理别人的、清整个临时目录 |
| **AfterAll** | 阶段三 | 整轮结束后 | **允许全局清理**：清产物、收进程、恢复环境 | —— |

> `Execute` 与 `AfterEach` 都属于阶段二 —— 它们只能管自己，
> 这正是「中途不清理环境」的落地形式。

## 三、四条附加原则

### 原则一：测试之间不得存在隐式依赖

**测试 B 不得依赖测试 A 已执行过，也不得依赖 A 留下的数据。**

每个用例都必须能独立运行。落实方式：
- 每个套件支持 `--only <case>`，任何时候都能单跑任一个
- `BeforeEach` 必须先清掉同名用例的旧资源（防止上次中断留下的脏状态）

**反例**：`T21 配置损坏后重建` 依赖 `T20` 先写出配置 —— 这类必须改成
在 `T21` 自己的 `BeforeEach` 里显式准备前置状态。

### 原则二：测试资源必须有明确归属

**每个测试创建的资源，都必须能追溯到对应的测试。**

目录布局强制为：

```
%TEMP%\Auto7zTest_data\<套件名>\
    Auto7z\                    ← 产品数据目录（套件内共享，这是有意的）
    cases\
        <用例A>\               ← 用例 A 独占
            res1.txt
            tmp\
        <用例B>\               ← 用例 B 独占
```

清理时**按登记表删**（`Lifecycle.own(...)` 登记过的路径），
绝不允许「扫整个临时目录按模式删」—— 那会误删别的用例正在用的东西。

### 原则三：清理操作必须具备幂等性

**清理一次和清理多次，最终效果必须一致。**

- 删除不存在的资源不报错
- `after_each()` 可重复调用
- `after_all()` 可重复调用
- 即使前面断言抛异常，`finally`/`__exit__` 里的清理仍要执行

### 原则四：每次执行都必须可核对

**「写好了」不等于「在跑」；「显示通过」也不等于「真的跑过」。**

这一条是 2026-11-23 两次教训换来的：

1. 审计发现 **19 个测试工具零引用** —— 写好了却孤立地放在目录里，等于不存在。
   其中 4 个一旦被调用就崩溃（`NameError: safe_rmtree`）。
2. 再审计发现 **4 个探针「被调用但从未执行」** —— 聚合器里漏了
   `code, text = run(...)`，却拿**上一个探针的遗留变量**去判定。
   而那次的遗留值恰好是 rc=0，于是**没跑的探针被记为通过**。

第 2 类最危险：任何「未执行」防护都抓不到它，因为状态被赋成了「通过」。

**硬性要求**：

- 结果对象的默认状态必须是「未执行」，不能是「跳过」。
  「跳过」是**主动**声明（有显式理由）；「未执行」是缺陷。
  把默认值设成「跳过」，漏赋值的路径就会伪装成一次正常跳过。
- 汇总时必须**对账**：记录每次真实执行，核对每个结果项是否真的对应一次执行。
  只查 `status` 字段不够 —— 它可能是别人留下的。
- 任何「未执行」一律计入失败，不能只体现在总数少了几项。
- 新增检查项时同步更新 `EXPECTED`（见 `run_regress.py` 里那条断言，
  它会报「预期 N 项、实际 N-1 项，说明有检查没跑到」）。

## 四、串行 vs 并行的判据

阶段二**必须串行**。这不是保守，而是共享环境下的正确选择。详见第一节的相关小节。

共享资源竞争的真实后果：

| 问题 | 影响 |
|---|---|
| 配置键冲突 | A 改配置 → B 读到错配置 |
| 数据竞争 | 一个测试删掉另一个正在用的数据 |
| 资源独占 | 争抢同一端口 / 设备 / 文件 |
| 环境清理冲突 | 一个测试清环境，另一个还在跑 |
| 状态污染 | 前一个的状态影响后一个的结果 |

### 本项目特有的硬约束

产品有**单实例互斥体**。并行跑两套测试时，第二套会拿不到互斥体，
表现为 `taborder` 报「走查中焦点丢失」这类假失败 ——
本轮就实际踩过一次（回归 + 系统测试同时跑 → 系统测试 1 项失败，串行重跑 18/18 全绿）。

**升级到并行的前提**（四条全部满足才可尝试）：
1. 数据隔离：每套件独立数据根（本项目已有：`%TEMP%\Auto7zTest_data\<suite>`）
2. 配置隔离：每用例独立配置（规范已要求，尚未全部落实）
3. 资源隔离：不共用互斥体 / 端口 / 固定路径
4. 环境隔离：`BeforeAll`/`AfterAll` 的全局操作不与其他套件重叠

补齐这四条之前，**不允许引入并行执行**。

## 五、实现方式

所有套件必须使用 `test_lifecycle.py` 的 `Lifecycle`，不得自行发明清理顺序：

```python
from test_env import isolate_data_root
DATA_ROOT = isolate_data_root("mysuite")   # 必须最早，在 import config_guard 之前

from test_lifecycle import Lifecycle
with Lifecycle("mysuite") as lc:
    for case in cases:
        case_dir = lc.before_each(case)    # 只建自己的
        res = case_dir / "res.txt"
        lc.own(res)                        # 登记归属
        run_case(case)                     # 执行
        lc.after_each()                    # 只清自己的
# __exit__ 里自动 after_all（含失败路径）
```

### 必须遵守的细节

| 项 | 要求 |
|---|---|
| 子进程 | 必须 `lc.track_process(proc)`，否则残留进程会锁住数据目录 |
| 环境变量 | `AfterAll` 必须 `pop(AUTO7Z_DATA_ROOT)`，不留改道痕迹 |
| 删除闸门 | 任何 `rmtree` 前必须过 `_assert_safe`（在 `%TEMP%` 下且含标记串） |
| 失败清理 | 清理放 `finally` 或 `__exit__`，不得只在成功路径清理 |
| 现场保留 | 调试时设 `AUTO7Z_TEST_KEEP=1` 保留产物 |

## 六、违规检查清单

接手时按此清单核对，任一项不满足即为回归：

- [ ] 套件使用 `Lifecycle`，而非自建清理逻辑
- [ ] `BeforeAll` 里做了上一轮遗留清理
- [ ] `BeforeEach` 只建当前用例目录，不碰共享状态
- [ ] 用例内**没有**全局清理调用（`rmtree(整个临时根)` 之类）
- [ ] 资源通过 `own()` 登记，清理按登记表走
- [ ] `AfterEach` / `AfterAll` 幂等，重复调用不报错
- [ ] 子进程都经过 `track_process`
- [ ] `AfterAll` 恢复了环境变量
- [ ] 每个用例可 `--only` 单跑
- [ ] 删除前都过 `_assert_safe`
- [ ] 套件之间不并行（当前阶段）
- [ ] **结果对象的默认状态是「未执行」，不是「跳过」**
- [ ] **汇总时对账「每个结果项是否真的对应一次执行」，而不只看 status 字段**
- [ ] **新增/删除检查项时同步更新 `EXPECTED`**
- [ ] **检查器做过变异测试（注入违规能 FAIL，恢复后 PASS）**
- [ ] **「跑产品」的检查器在变异后重新编译过**

## 七、历史事故对照

| 事故 | 根因 | 规范条目 |
|---|---|---|
| 并行跑出 23 项假失败 | 两套件共用数据根，配置互相覆盖 | 一（串行）+ 原则二 |
| 测试脚本删掉产品数据目录 | 清理时扫整个目录按模式删 | 原则二（按登记表删）+ `_assert_safe` |
| 回归 + 系统测试并行 → `taborder` 假失败 | 单实例互斥体竞争 | 一、阶段二为什么必须串行 |
| 残留 GUI 进程锁住数据目录，下一轮清理失败 | 子进程未登记收尾 | 四、`track_process` |
| 某用例单独跑必失败、整套跑才通过 | 依赖前置用例留下的数据 | 原则一 + `--only` |
| 新增「UI 取消按钮」检查静默消失 | `NameError` 被 `try/finally` 吞掉，`res.add` 从未执行 | 原则四 + `EXPECTED` 断言 |
| 四个外壳探针从未执行却显示通过 | 沿用上一个探针的 `rc=0`，状态被赋成「通过」 | 原则四（执行台账对账） |
| Release 下「LoadLibrary 失败」被显示为跳过 | `is_release_skip` 用 `code == 3` 判定 | 原则四（只认显式标记） |
| 20 项全过但退出码 1 | 清理阶段 `safe_rmtree` 未 import | 原则三（清理幂等且不崩） |
| 19 个测试工具零引用 | 写好了但从未接入任何套件 | 原则四（每次执行都必须可核对） |
| `cmdcontract_check` 被误判为漏报 | 变异后没重新编译，跑的是旧二进制 | 原则四（变异测试前提） |

| `.config` 便携配置残留导致回归读错配置 | `AfterAll` 未恢复环境 | 五、环境变量恢复 |
